# Публикация групп модель → AlfaCRM (этап 3) — дизайн и основа

Направление: **модель → CRM**. Из панели одной кнопкой создавать в AlfaCRM группу,
её расписание и состав (+ при необходимости абонементы). Даты учебного года:
**старт 02.09.2026, окончание 31.05.2027**.

> Статус: **инструмент готов и подключён к интерфейсу** (кнопка «📤 Опубликовать в Alfa» на вкладке
> «Группы», только админ). Живая запись возможна только вручную: сухой прогон → подтверждение →
> первый запуск принудительно ограничен ОДНОЙ группой. Агент в Alfa не писал ни разу.
> Детей по умолчанию НЕ привязываем (галочка выключена) — состав переносим отдельно в августе.

## Точные поля API Alfa (из исходников, проверено)

Все — `POST /v2api/{branch}/{объект}/create`, заголовок `X-ALFACRM-TOKEN`.

### group (группа)
| поле | что | из модели |
|---|---|---|
| `name` | название группы | `l.group` (поле «Группа» занятия) |
| `branch_ids` | `[int]` филиалы | `[branch]` из config |
| `teacher_ids` | `[int]` педагоги | по имени `l.teacher` → id (нужен справочник педагогов) |
| `level_id` | уровень | ⚠️ уточнить (может быть обязателен) |
| `status_id` | статус группы | ⚠️ уточнить (напр. «активная») |
| `limit` | вместимость | `l.students` (или groupSize курса) |
| `note` | заметка | курс/примечание |
| `b_date`,`e_date` | период | 2026-09-02 … 2027-05-31 |

### regular-lesson (регулярное расписание группы)
| поле | что | из модели |
|---|---|---|
| `related_class` | `"Group"` | константа |
| `related_id` | id созданной группы | из ответа group/create |
| `subject_id` | предмет | `l.course` → subject_id (справочник subject) |
| `teacher_ids` | `[int]` | как у группы |
| `room_id` | кабинет | `l.room` → room_id (справочник room) |
| `day` | день недели | `l.day` ⚠️ сверить нумерацию Alfa (у нас 1=Пн..7=Вс) |
| `time_from_v`,`time_to_v` | время | `l.start`/`l.end` в формате `HH:MM:00` |
| `lesson_type_id` | тип занятия | справочник lesson-type (обычное занятие) |
| `b_date`,`e_date` | период | как у группы |
| `is_public` | показывать | true |

Группа 2×/нед = **две** regular-lesson (или одна с `days:[..]`).

### cgi (ученик ↔ группа)
| поле | из модели |
|---|---|
| `customer_id` | `kid.alfaId` (уже проставлен синхронизацией контактов) |
| `group_id` | id созданной группы |
| `b_date`,`e_date` | период учебного года |

### tariff / customer-tariff (абонементы — опционально, позже)
`tariff`: type, name, price, lesson_count, duration, branch_ids.
`customer-tariff`: customer_id, tariff_id, subject_ids, b_date, e_date, balance…

## Что уже готово на сервере (в этом прокси)
- `?action=refs` — тянет справочники Alfa для маппинга: **subjects, rooms, lesson-types**
  (и пытается получить педагогов/статусы/уровни; что вернётся — то и покажем).
- `?action=publish` (POST, **по умолчанию dryRun=true**) — принимает план одной группы
  (`{group, schedule[], studentAlfaIds[]}`) и:
  - при `dryRun:true` — возвращает готовые payload'ы, **ничего не создавая** (для проверки);
  - при `dryRun:false` — создаёт группу → расписание → привязку учеников, возвращает id.

Дополнительно (READ, добавлено для этапа 3):
- `?action=groupsList` — все группы Alfa: id, name, subject_ids, teacher_ids, status_id, level_id,
  limit, note, b/e_date, is_archive + `sample` (сырая первая запись — сверить имена полей).
- `?action=regularLessons` `{groupId}` — регулярное расписание существующей группы: day, time_from,
  time_to, room_id, teacher_ids + `sample`. Именно этим определяется нумерация дня недели **без
  пробной записи в CRM**.

## Открытые вопросы — как они закрыты

| Вопрос | Как решено |
|---|---|
| Справочник **педагогов** | `refs` пробует `teacher/index`. Если Alfa его не отдаёт — в UI вместо выпадашки поле «id вручную», либо оставить пусто (группа создастся без педагога, назначить в Alfa). |
| **`status_id` / `level_id`** | Не угадываем: если справочника нет, варианты собираются из **реально встречающихся значений у существующих групп** (`groupsList`). Есть пункт «— не отправлять —». |
| **Нумерация `day`** | Кнопка «🔎 Определить по существующей группе»: читаем `regularLessons` и сверяем дни Alfa с нашими по совпадению времени. Режимы: `1=Пн…7=Вс`, `0=Пн…6=Вс`, `1=Вс…7=Сб`. Если ни один не совпал — говорим прямо и режим НЕ меняем. |
| **Курсы ↔ subjects** | Авто по названию: точное → «семейство курса» без «(1 час)» → однозначное вхождение. Неоднозначное **не угадываем** — правится руками, выбор хранится в `S.alfaMap` (уезжает в Firebase). |

## ⚠️ Грабли, на которые уже наступили
**Список групп Alfa приходил обрезанным** — и почти всё выглядело «новым» (готовый рецепт наделать
дублей). Две причины, ровно те же, что когда-то были с выгрузкой клиентов:
1. **Группы лежат по ФИЛИАЛАМ**, а запрос шёл в один (`alfa_branch()`). Группа из другого филиала
   просто не находилась. Теперь обходим `alfa_all_branch_ids()` с дедупом по id, в ответе — `branches`
   (сколько нашли в каждом филиале), у каждой группы — её `branch`.
2. **Alfa режет страницу до ~50 записей.** Просили `count:100` и крутили цикл по условию
   `count($items) === 100` → после первой же страницы (50 штук) цикл обрывался. Теперь `perPage=50`
   и «продолжаем, пока страница ПОЛНАЯ» (`total` Alfa возвращает не всегда).

В модалке есть блок **«🔍 Что мы видим в Alfa»** с поиском: если группа в Alfa есть, а в списке её нет —
значит она не попала в выгрузку, и это надо чинить ДО публикации, а не после.

## Филиалы — отдельное измерение (Жанна работает с филиалами 1 и 2)
- **Кабинеты в Alfa принадлежат филиалам**, id у одноимённых кабинетов разные. Поэтому `refs`
  собирает справочники ПО ФИЛИАЛАМ (дедуп по id), у кабинетов и педагогов есть поле `branch`,
  а в списке они подписаны «3 этаж · Прознание (#1)».
- **Филиал группы определяется её кабинетом**; если кабинет не сопоставлен — берётся «филиал по
  умолчанию» из настроек. В строке таблицы прямо написано, куда ляжет группа.
- Группа, у которой занятия в кабинетах **разных филиалов**, публиковаться не даёт (⛔): одна группа
  не может лежать в двух филиалах, это надо решить руками.
- `publish` принимает `branch` и создаёт группу/расписание/связи **строго в нём**
  (`alfa_call_branch`). Раньше молча писал в авто-определённый филиал — половина групп ушла бы не туда.
- `refs`/`groupsList` принимают `branches:[1,2]` — сузить обход (меньше запросов, меньше риск
  таймаута шлюза). В UI это чекбоксы «Филиалы, с которыми работаем»; их смена перечитывает справочники,
  потому что id кабинетов у филиалов свои.

## Защита от дублей (главный риск)
Сверка с существующими группами Alfa идёт по двум ключам: **точное** имя (`_normCourse`) и имя
**без скобок/длительности** (`_courseBase`) — иначе наша «Scratch (1 час) 2» не находит альфовскую
«Scratch 2» и мы создаём дубль. Точное совпадение → «уже есть», по базе → «похоже на …».
Оба состояния по умолчанию **пропускаются** (галочка снята), но их можно включить руками.
Плюс: id созданной группы пишется в `S.groupMeta[key].alfaId` — такая группа больше не публикуется
(и переживает переименование курса, т.к. `groupMeta` мигрирует вместе с ключом).

## Безопасный порядок запуска (в интерфейсе)
Вкладка «Группы» → «📤 Опубликовать в Alfa» (только админ):
1. Модалка тянет `refs` + `groupsList`, авто-сопоставляет курсы/педагогов/кабинеты;
   несопоставленное подсвечено красным. Выбрать шаблон имени — рядом показано, **сколько имён
   совпало с существующими группами Alfa** (больше совпадений = меньше риск дубля).
2. «🔎 Определить по существующей группе» — нумерация дня недели.
3. «👁 Сухой прогон» — показывает готовые payload'ы (первые 10 отмеченных), в Alfa НЕ пишет.
4. «📤 Создать в Alfa» — два подтверждения; **первый живой запуск принудительно ограничен одной
   группой**. Открыть её в Alfa, проверить день/время/кабинет — и продолжить остальными.
5. Если группа создалась, а расписание частично упало — id всё равно записывается (дубля не будет),
   в журнале модалки видно, какие шаги упали; подробности ошибки Alfa — в консоли (F12).

## Что осталось на живую сверку (только с боевым токеном)
- Примет ли Alfa `regular-lesson` с нашими полями (`time_from_v`/`time_to_v`, `lesson_type_id`) —
  первая тестовая группа покажет; ошибки шагов возвращаются целиком (`sent` + ответ Alfa).
- Обязателен ли `status_id`/`level_id` — если да, Alfa ответит ошибкой валидации на тестовой группе.
- Отдаёт ли Alfa справочник педагогов (`refs.teachers`) — видно сразу при открытии модалки.
